Infinity LIS · instrument interfaces

ASTM Interface Architecture

How laboratory analyzers talk to the Infinity LIS through this service: the modules, how the service starts and listens, how results, queries and orders move between the analyzers, RabbitMQ, the core LIS and SQL Server, and what is still open. Covers ORTHO VISION (blood bank) and Sysmex XN (hematology).

Standards: ASTM E1381-02 (link) · E1394-97 (records) Java 8 target · Spring Boot 2.7.18 Updated 2026-11-17 · branch claude/adoring-shannon-jmlq1n (PR #1)

01At a glance

The service is a TCP server. Each analyzer connects to its own port and speaks ASTM. The service checks every frame, turns each complete message into JSON, keeps an audit copy in SQL Server and publishes the JSON to RabbitMQ for the core LIS. Orders travel the other way: the core LIS publishes JSON, the service stores it, converts it to ASTM and sends it when the analyzer is connected.

ORTHO VISION blood bank

  • Instrument name OrthoVision, port 9001
  • Driver OrthoVisionDriver
  • Records H P Q O R M L; M carries card and well results
  • Sends queries, results and keep-alives; receives orders
  • Spec notes: astm_message_specs.md
  • Status: worked against the real analyzer in 2025

Sysmex XN hematology

  • Instrument name SysmexXN, port 5000
  • Driver SysmexXnDriver + SysmexXnSpecimenId
  • Records H P Q O R C S L; C comments are parsed
  • Sends inquiries, patient, QC and slide results; receives order responses
  • Spec: Sysmex XN ASTM Host Interface (NA rev 11)
  • Status: spec examples pass as tests; simulator test next, then the real IPU

04How the service starts and opens ports

  1. Windows service starts the JAR. NSSM (see README) runs java -jar astm-server-1.0.0.jar --spring.profiles.active=prod. Spring Boot loads application.properties and application-<profile>.yml; secrets come from environment variables (DB_PASSWORD, RABBITMQ_PASSWORD, ...).
  2. Connections are prepared. Hikari pool to SQL Server; RabbitMQ connection factory with publisher confirms (correlated), publisher returns and mandatory=true, on vhost infinity-lis-<env>.
  3. Order listeners start (InstrumentQueueConfig, only when lis.messaging.enabled=true). With declare-topology: false nothing is created on the broker. One listener container starts per distinct order queue, so both analyzers share one consumer on lis.orders.instrument.astm.outbound.q.
  4. One listener thread per instrument (ASTMServer, @PostConstruct). For each enabled instrument with a driverClassName, thread ASTM-Listener-<name> opens ServerSocket(port) on all network interfaces and loops on accept() with a 2 s timeout. Log line: Listener started for 'SysmexXN' on port 5000 using driver ...
  5. Scheduled jobs start. Order retry every lis.messaging.retry.schedule-interval-ms (60 s); result republish every 2 min.
  6. An analyzer connects. Any older session for that instrument is stopped and replaced. The socket gets TCP keep-alive, no-delay and a 500 ms read timeout. A new driver instance is created and the session runs on a pooled ASTM-Conn-* thread.
  7. Session loop (InstrumentConnectionHandler): send at most one queued order, then poll the socket for 500 ms; repeat. Incoming ENQ always wins over sending.
  8. Shutdown (@PreDestroy): listeners close, sessions stop, orders still queued in memory go back to PENDING in the database, threads get 5 s to finish.

05Many analyzers in one deployment

Running ORTHO VISION, Sysmex XN and future ASTM analyzers in one service is fine and is the intended design. Each analyzer costs two threads (listener and session) and one socket.

isolated per analyzer

  • Port and listener thread
  • Session thread, socket, driver instance, in-memory order queue
  • Protocol state and timers
  • A parse error or bad frame affects only that analyzer

shared by all analyzers

  • The Java process: a restart drops every session (analyzers reconnect and resend unacknowledged messages)
  • SQL Server pool (5 connections local) and the RabbitMQ connection
  • The two retry jobs
  • The single ASTM order queue (orders are routed by instrumentName)

06The wire: E1381 framing

The link layer is the same for every analyzer (ASTMProtocolStateMachine). Wire charset is ISO-8859-1, so accented names survive and the checksum is computed on bytes.

ENQ→ ACK ← STX1H|\^&|||...ETXC1 C2CR LF→ ACK ← STX2P|1|...ETXC1 C2CR LF… frames 3, 4 … 7, 0, 1 … EOT
  • Frame number 1..7, then 0, 1, ...; checksum = 8-bit sum of the bytes after STX up to and including ETX/ETB, two uppercase hex digits.
  • One record per frame. The Sysmex spec forbids splitting a record across frames on TCP, so outgoing records are sent whole. Records can be split into ETB frames with sendMessage(msg, maxFrameDataSize) if a future analyzer needs the 240-character limit. Incoming ETB frames are joined.
  • The receiver rebuilds the message with one record per line (CR LF); drivers split on CR.
  • A bad checksum gets NAK and the sender repeats the frame (up to 6 times). A repeated frame the receiver already ACKed is ACKed again and dropped.
Timer / ruleValueMeaning
Sender waits for ACK15 sNo reply: frame failed, transfer ends with EOT
Receiver waits for next frame30 sSilence: transfer abandoned, message discarded
ENQ contention back-off20 sBoth sides sent ENQ: the service yields, receives first, retries its order later

08Flow: results from the analyzer

  1. Link layer validates every frame and ACKs it; the analyzer moves on frame by frame.
  2. On EOT the session gets the whole message, types it (RESULT, QUERY, KEEP_ALIVE, ...) and skips keep-alives.
  3. Row inserted in AnalyzerInboundMessages with the raw text and remote address (RECEIVED).
  4. The instrument's driver parses it into AstmMessage; the instrument name is stamped on it.
  5. Only messages with results or queries continue; the row becomes PROCESSED.
  6. Published to lis.inbound.x with the routing key for its type, headers instrumentName, messageType, resultCount, orderCount. The service waits for the broker confirm and checks the message was routed; then PUBLISHED.

11RabbitMQ topology

Standard Infinity LIS topology, provisioned by infinity-lis-rabbitmq-topology.ps1 (platform script, not in this repo). Verified on the dev broker 192.168.20.254 on 2026-11-16.

FlowExchangeRouting keyQueue
Patient results (RESULT)lis.inbound.xresults.instrument.astmlis.results.instrument.inbound.q
QC results (QC_RESULT)lis.inbound.xqc.instrument.astmlis.qc.instrument.inbound.q
Queries (QUERY)lis.inbound.xresults.instrument.astm.querylis.results.instrument.inbound.q (no query lane yet)
Orders to analyzerslis.outbound.xorders.instrument.astm.worklistlis.orders.instrument.astm.outbound.q
Order cancelslis.outbound.xorders.instrument.astm.cancelsame order queue (no special handling yet)
  • All exchanges are topic exchanges. Every work queue is a quorum queue with a delivery limit, reject-publish overflow and a paired .dlq on lis.dlx (original routing key kept).
  • User astm-server may publish only to lis.inbound.x and consume only the ASTM order queue; it cannot create anything. Hence lis.messaging.declare-topology: false in every profile.
  • lis.results.instrument.inbound.q is shared with Mirth (HL7 analyzers). Never purge it.
  • Routing per type is AppConfig.InstrumentConfig.routingKeyFor(); it ignores a RETRY_ prefix and falls back to resultsRoutingKey when qcRoutingKey or queryRoutingKey is empty.

12Database tables

SQL Server, in the service's own database, separate from the Core LIS databases: infinity-lis-astm-dev (local, dev), infinity-lis-astm-stage, infinity-lis-astm-prod (override with DB_NAME). Plain JDBC; only this service reads or writes these tables. Table names state the direction relative to the LIS, as the RabbitMQ names do (lis.inbound.x, lis.outbound.x).

  • Create once per environment: run astm-server/src/main/resources/db/astm-schema.sql in the new database (safe to run again). The application never creates tables. The script also has optional, commented sections for a least-privilege login (db_datareader + db_datawriter on this database only) and for copying history from the old tables.
  • Renamed 2026-11-17: ASTMServerMessages → AnalyzerInboundMessages, ASTMOrderMessages → AnalyzerOutboundOrders; same columns. The old tables in the Core LIS database (infinity-lis-shard-1, infinity-lis-staging) are no longer used.
  • SchemaScriptTest fails the build when a table, column or status used by the repositories is missing from the script.

AnalyzerInboundMessages

Every message received from an analyzer (except keep-alives). Audit trail and publish retry list.

Deploying on Windows

  1. mvn -B clean package (JDK 17, 21 or 25; output runs on Java 8+). Deploy astm-server/target/astm-server-1.0.0.jar.
  2. Install as a Windows service with NSSM; set the environment variables on the service.
  3. Open each analyzer port, limited to that analyzer: New-NetFirewallRule -DisplayName "ASTM SysmexXN" -Direction Inbound -Protocol TCP -LocalPort 5000 -RemoteAddress <IPU IP> -Action Allow
  4. Sysmex IPU: change only Host Computer 1 IP and port (format stays XN series ASTM1381-02/ASTM1394-97); leave Host Computer 2 alone. Roll back from the lab's screenshots.
  5. Logs: rolling files under LOG_PATH (default D:/astm-interface-services-data/logs in local), plain text and HTML, 30 days kept.

Adding an analyzer: write a driver with tests built from the vendor's example messages, add an instrument entry to every application-*.yml, add a simulator test-case file, update this page.

The question is whether the SQL Server connection can go too.

What the database does today

JobWhy it mattersRabbitMQ-only replacement
1. Audit of every raw messageProof of what the analyzer sent; troubleshootingPublish an audit event (raw text, status changes) to a new audit.instrument.astm lane; the core LIS stores it
2. Outbox when the broker is downThe analyzer keeps sending; results must not be lostStill needs a local durable store: a small embedded file database on the service machine (no network DB)
3. Holding orders until the analyzer connectsAnalyzers go offline for maintenanceKeep orders in RabbitMQ: per-instrument order queues consumed only while that analyzer is connected, acknowledged only after the analyzer ACKs
4. Order status and retriesKnow whether an order reached the analyzerPublish SENT/FAILED status events to the LIS on a new lane; the LIS shows them (today the LIS cannot see order delivery at all)

for

  • No database credentials or schema on the instrument server
  • One owner for all data; the LIS can show order delivery status
  • Simpler deployment: JAR, broker credentials, firewall rule

against / cost

  • New lanes in the topology script and new consumers in the core LIS
  • A local store is still needed for broker outages
  • Order handling changes (per-analyzer queues, acknowledge after delivery)
Recommendation

Yes, it is possible and it is the cleaner boundary, as long as a small local outbox stays on the service machine. Do not send application log files over RabbitMQ; keep them as rotating local files and publish only the business events (audit and order status). Keep SQL Server for the current simulator, stage and Sysmex go-live tests, as decided, but in the service's own ASTM database, not a Core LIS database (done 2026-11-17: the Core LIS no longer shares any storage with this service). Then, if wanted, move in three steps: (1) add the audit and order-status events alongside the database; (2) let the core LIS consume and store them; (3) replace SQL Server with the local outbox and per-analyzer order queues.

18Keeping this page true
